## 2. Taxonomy decision — broad material classes (Option 1)

The model classifies **whole images into 8 broad material categories**. It does
**not** identify subtypes (PET vs HDPE, AA vs lithium, glass colour, exact
e-waste). The earlier provisional taxonomy used specific names
(`plastic_pet_bottle`, `hazardous_battery_aa`, …) that no available dataset can
actually supervise — so the classes were narrowed to what the data proves.

| idx | class | model meaning |
|---|---|---|
| 0 | `battery_hazardous` | batteries / household hazardous items |
| 1 | `glass` | glass containers (all colours) |
| 2 | `metal` | metal packaging (all types) |
| 3 | `organic` | food & garden waste |
| 4 | `other_residue` | mixed residual waste |
| 5 | `paper_cardboard` | paper & cardboard |
| 6 | `plastic` | plastic packaging |
| 7 | `textile` | clothes, shoes, fabric |

Names are in **alphabetical order on purpose**: Ultralytics derives classification
class indices by sorting folder names, so `classes.json`, `data.yaml`, the folder
layout and the exported `CLASS_INDEX_MAP` agree by construction. `train.py`
writes its own canonical `data.yaml` and `export_onnx.py` refuses to export if the
checkpoint's `names` order differs from `ml/data.yaml`.

The backend renders guidance for these broad classes through
`app/services/inference/broad_classes.py` (honest, subtype-free copy). If a
predicted class is not in that layer **and** not in the demo pool, the result is
reported as `unknown` with safe "check local rules" guidance. A missing
`CLASS_INDEX_MAP` makes **every** prediction `unknown` (fail-safe, never guesses).

## 4. Workflow

```
ml/
  requirements-ml.txt     training deps (isolated venv; backend untouched)
  classes.json            canonical index -> class name (single source of truth)
  data.yaml               canonical dataset config (same order as classes.json)
  source_mapping.json     raw-source label -> model class mapping + provenance
  prepare_dataset.py      raw -> deduped, split, EXIF-stripped dataset (stdlib)
  validate_dataset.py     stdlib gate: structure, counts, signatures, leakage (exit 2 if unready)
  train.py                seeds + deterministic + early stopping + val/test metrics
  export_onnx.py          .pt -> verified .onnx + class-index-map.json (name-order checked)
  tests/                  pytest suite for prepare_dataset / validate_dataset
  runs/  models/  data/   (git-ignored; created on use)
```

Commands:

```powershell
# 1. build the training dataset from the raw source (already done)
python ml/prepare_dataset.py --source-root ml/data/raw --out ml/data/waste-classify `
    --dataset kaggle12 --seed 42 --val-frac 0.1 --test-frac 0.1 --max-per-class 1000

# 2. validate (must exit 0; add --json for a machine-readable report)
python ml/validate_dataset.py --data ml/data/waste-classify --json ml/data/waste-classify/validation_report.json

# 3. install the isolated ML stack (first time only, ~250-350 MB)
python -m venv ml/.venv
ml/.venv/Scripts/python -m pip install -r ml/requirements-ml.txt

# 4. train (CPU; use a Colab T4 for speed) -- REQUIRES APPROVAL
ml/.venv/Scripts/python ml/train.py --data ml/data/waste-classify --epochs 50 --device cpu

# 5. export + verify ONNX, write class-index map
ml/.venv/Scripts/python ml/export_onnx.py --weights ml/runs/<run>/weights/best.pt `
    --out ml/models/loopwise-yolo26n-cls.onnx
```

After export, copy the `.onnx` and `.class-index-map.json` to the server, install
`onnxruntime`+`numpy` in the backend env, and set:

```
MODEL_PATH=<abs path>/loopwise-yolo26n-cls.onnx
CLASS_INDEX_MAP=<abs path>/loopwise-yolo26n-cls.class-index-map.json
MODEL_VERSION=yolo26n-cls-v1
DEMO_MODE=false
```

No retraining from user corrections (human `reviewed=true` gate before any export use).

## 6. Honest limitations

- The classifier outputs **broad material classes only** — the app never claims
  PET/AA/aluminium/charger specifics.
- Accuracy is **unknown until training completes**; no metrics are quoted yet.
- Source label noise (and the 5 flagged cross-class hash groups) may cap accuracy.
- CPU-only on this machine; real training should run on a GPU (e.g. Colab T4).
- `other_residue` (`trash`) is a genuine catch-all and the hardest class.

## 7. Privacy & safety

- Raw images are never modified; prepared copies are EXIF-stripped.
- No faces/legible plates are targeted; no user photos are uploaded or trained on.
- No cloud deployment; the model runs locally in the backend's ONNX runtime.
- Low-confidence predictions (< `LOW_CONFIDENCE_THRESHOLD = 0.35`) and unmapped
  classes return the safe `unknown` result — never a fabricated material.
